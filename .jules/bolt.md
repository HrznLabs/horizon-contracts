## 2024-03-03 - [Storage Pointer Optimization]
**Learning:** Using storage pointers for struct manipulation is a highly effective optimization in Solidity, especially for multiple writes to the same mapping element. `PackedRating storage rating = _ratings[...]` avoids memory-to-storage copies and redundant mapping lookups.
**Action:** Always prefer storage pointers when updating multiple fields of a struct located in storage, rather than loading the whole struct into memory, modifying it, and writing it back to storage.
## 2024-06-12 - Caching State Variables in Internal View Functions
**Learning:** In Solidity, caching a frequently accessed state variable (like `missionFactory`) into a local stack variable inside internal helper functions (such as `_isFactoryEscrow`) that are called multiple times via modifiers avoids redundant secondary `SLOAD` operations, measurably reducing gas consumption without affecting logic.
**Action:** Always scan internal view helpers that retrieve state variables for multi-use patterns (e.g., checking for zero-address before making an external call on the same address). Cache the state variable to a local stack variable to save gas.
## 2024-06-27 - [Storage Pointer Struct Field Caching Optimization]
**Learning:** In `HorizonAchievements.sol`, when modifying multiple storage slots or passing fields from a `storage` pointer to mapping keys (like `_userHasAchievement[achievement.typeId][from] = false;`), caching the frequently accessed struct field (e.g., `achievement.typeId`) into a local stack variable (`uint256 typeId`) avoids redundant `SLOAD` operations or mapping lookups and significantly reduces gas consumption.
**Action:** Always cache struct fields into local stack variables when they are accessed multiple times within a function, especially when those fields are used as keys in state mappings.
## 2024-06-28 - [Dead Code Removal in Access Control]
**Learning:** In OpenZeppelin's `AccessControl`, calls to `_revokeRole` perform mapping lookups which cost gas. If a function already verifies that a user *does not* have a certain role (and reverts early if they do), subsequent `_revokeRole` calls for those specific roles are dead code and safe to remove, measurably saving gas (e.g., removing two redundant `_revokeRole` calls saved ~645 gas in `GuildDAO.sol`).
**Action:** When auditing or optimizing access control functions, always ensure that role revocation or assignment operations are strictly necessary. Avoid performing state updates on roles that have already been validated in earlier assertions.
## 2024-07-31 - Loop Fusion and State Deletion Optimization
**Learning:** In `FeeDistributor.sol`, looping over `guilds.length` multiple times inside `distribute()` - once to calculate/pay guilds and another time to reset `guildVolume` - leads to redundant iterations. We can fuse the state deletion loop into the main payment loop, completely eliminating the secondary `O(N)` loop. Importantly, we must perform the `delete guildVolume[guild]` operation *unconditionally* for every registered guild in the fused loop. If a guild has zero volume, we must still delete the volume to clear the state and handle the case without bypassing the deletion via `continue`.
**Action:** When iterating over a list to distribute funds and subsequently clear balances, fuse the loops. But when doing so, ensure state clearing (`delete`) occurs unconditionally before any early returns (like `if (vol == 0) continue`), by caching the balance to memory first.
